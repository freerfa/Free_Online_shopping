# 06 — Payments

The store has a **two-sided** payment system:

- The **customer side** — saved payment methods, paying for an order.
- The **admin side** — a ledger of advertising-fee payments.

A single master switch, `site.payment_enabled`, turns the whole system on
or off.

---

## 1. The master switch

```python
def payment_enabled():
    """Whether the customer-facing payment system is switched on."""
    return bool(get_blob("site", {}).get("payment_enabled", True))
```

It is toggled at **Admin -> Payment settings**
(`POST /admin/settings/payments`):

```python
site["payment_enabled"] = request.form.get("enabled") == "on"
set_blob("site", site)
```

The default is `True` — the payment system is on unless an admin turns it
off.

### 1.1 What happens when it is off

| Page | Behaviour |
|---|---|
| `/user/payment` | Flashes *"The payment system is currently disabled."* and redirects to `/account` |
| `/order/pay/<oid>` | Same — redirects to `/account` |
| `/myproducts` | Same — redirects to `/account` (posting requires the payment system) |
| `/checkout` | Renders normally, but **only Cash on Delivery is accepted**; any other method is rejected with *"The payment system is currently disabled. Only Cash on Delivery is available."* |
| `/admin/payments` | Flashes and redirects to itself |
| `/admin/listings` | Flashes and redirects to `/admin/payments` |

Cash on Delivery keeps working so the shop can still take orders while
payments are paused.

## 2. Payment methods

Defined in `PAYMENT_TYPES`:

| Key | Label | Extra fields captured |
|---|---|---|
| `visa` | Visa Card | `card_last4` (last 4 digits only), `card_name` |
| `mtn_momo` | MTN Mobile Money | `phone`, `provider = "mtn"` |
| `airtel_money` | Airtel Money | `phone`, `provider = "airtel"` |
| `bank_transfer` | Bank Transfer | `bank_name`, `account_name`, `account_last4` |
| `cod` | Pay on Delivery | — |

`cod` is treated specially throughout: it is the fallback that always works
when the payment system is off, and it is detected case-insensitively via
`chosen.lower() == "cod"`.

## 3. Saved payment methods

`GET,POST /user/payment` — requires `login_required` and the `payment`
permission.

Each method is stored on the user's record in the `users` blob:

```json
{
  "id": "pm_1a2b3c4d5e6f",
  "type": "mtn_momo",
  "label": "MTN Mobile Money",
  "is_default": true,
  "phone": "0771234567",
  "provider": "mtn"
}
```

The `id` is generated by `_pm_id()` as `"pm_" + secrets.token_hex(6)`.

### 3.1 Actions

| Action | Effect |
|---|---|
| `add` | Adds a method. The first method added becomes the default automatically. |
| `delete` | Removes the method with the submitted `pmid` |
| `default` | Makes the method with the submitted `pmid` the default (and clears the flag on the others) |

### 3.2 Security notes

- **No card data is stored.** For `visa` only the last 4 digits and the card
  name are kept. The full number is never written to disk.
- The submitted `ptype` is validated against `PAYMENT_TYPES` before anything
  is saved.
- All text fields are HTML-escaped with `html.escape()` before storage.

## 4. Paying for an order

`GET,POST /order/pay/<oid>` — requires `login_required` and the `payment`
permission.

The order is loaded by id; a missing order is a 404. On POST the `pay`
action:

1. Records the `payment_method` and `payment_reference` on the order.
2. Stores an optional receipt upload in `data/uploads/`.
3. Sets `payment_status` to `pending` and stamps `paid_at` when the admin
   later verifies it.

## 5. Checkout and order creation

`POST /checkout` writes the `orders` row with:

| Column | Value |
|---|---|
| `payment_method` | The chosen method label |
| `payment_status` | `pending` |
| `status` | `pending — <method>` — the human-readable summary |

Then it redirects:

| Method | Redirect |
|---|---|
| Cash on Delivery | `/order/<id>` |
| Anything else | `/order/pay/<id>` |

Stock is decremented for every cart item at checkout time, floored at 0.

## 6. The admin ledger

`admin_payments` records the **advertising fee** that sellers owe for
marketplace posts.

| Column | Notes |
|---|---|
| `type` | Always `ad_fee` for rows created through the UI |
| `user_id` | The username the fee relates to |
| `amount` | Fee amount |
| `method` | How it was paid |
| `status` | `pending` on creation, then `paid` or `rejected` |
| `reference` | Transaction reference |
| `receipt_path` | Optional receipt upload |

The fee amount itself lives in the `fees` blob as `per_post` (default
`5000`) and is set from **Admin -> Listings** with the `fee_set` action.

### 6.1 Recording a fee payment

The `record` action inserts a row with `status = 'pending'`. The admin then
verifies or rejects it with the `verify` / `reject` actions.

### 6.2 Per-listing fee status

Marketplace posts also carry their own `fee_status` field (`paid` /
`unpaid`), toggled from the Listings or Listing review page. This is
separate from the ledger: the ledger records a *transaction*, the product
field records the *state of that seller's obligation*.

## 7. Email

Order confirmation is emailed through `send_email_https()`, which uses the
Resend HTTPS API when `RESEND_API_KEY` is set and otherwise logs the
message. SMTP is avoided because it is commonly blocked on PaaS hosts.

See [08-uploads-security.md](08-uploads-security.md) for the email details.

## 8. Permissions

The `payment` permission flag gates the customer payment routes:

| Route | Flag |
|---|---|
| `/user/payment` | `payment` |
| `/order/pay/<oid>` | `payment` |

`/checkout` is gated by `shop` instead — it is the ordering flow, not the
payment flow, and it must still work with Cash on Delivery.

See [04-access-rights.md](04-access-rights.md).

## 9. Testing

| # | Scenario | Expected |
|---|---|---|
| 1 | Add a payment method, then a second one | The first is the default; the second is not |
| 2 | Click "make default" on the second | The default flag moves |
| 3 | Delete a method | It disappears from the list |
| 4 | Turn the payment system off | `/user/payment` and `/order/pay` redirect to `/account` |
| 5 | Check out with payments off | Only COD is accepted |
| 6 | Check out with a card method | Redirects to `/order/pay/<id>` |
| 7 | Record an ad-fee payment as admin | A `pending` row appears in the ledger |
| 8 | Verify that row | Its status becomes `paid` |
| 9 | Set the ad fee to a new amount | It is used for the next post |
| 10 | A customer without the `payment` permission | Both payment routes redirect to `/` with a flash |
